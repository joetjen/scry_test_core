# Changelog

## [Unreleased]

### Added

- A fifth `Scry.Test.Core.Conn` constructor, `timescaledb/1` -- the exact same `Scry.Engine.Postgrex` module `postgres/1` uses, entirely unmodified, pointed at a real, external TimescaleDB instead of plain Postgres. This is empirical, not asserted: `impl_spec.md`'s own roadmap names a dedicated `scry_engine_timescaledb` adapter as the intended way to validate the `scry_reltime` composite (relational + time-series) architecture, but investigation found nothing for a dedicated adapter to actually do differently today -- TimescaleDB speaks the plain Postgres wire protocol, and the language has no time-bucketing/hypertable construct yet to compile specially. Separately confirmed that the composite's real value already exists with zero new code: `Scry.TimeSeries.Executor.run/5` lowers `LAST` into an ordinary `WHERE` predicate recursively, including inside a nested/correlated `SELECT` (Scry's own `JOIN`-equivalent), before any engine ever sees it -- so a relational-join-shaped query with a time-series filter already works against any plain `Scry.Core.EngineBehaviour` engine. `timescaledb/1` reuses the existing `load_postgres_table/3` helper as-is (no TimescaleDB-specific DDL needed, confirming there's nothing to add) and a new `timescaledb_connection_opts/0` (`TSDB_HOST`/`TSDB_PORT`/`TSDB_USER`/`TSDB_PASSWORD`/`TSDB_DATABASE`, defaulting to `localhost:5434`, database `scry_test_core_timescaledb`).
  New `docker-compose.yml` service (`timescale/timescaledb:latest-pg16`, a different host port/database name than the existing `postgres` service and `scry_engine_postgrex`'s own compose file, so all three can run at once) and a new `mix test.timescaledb` alias (`test --include timescaledb`). `timescaledb/1`'s own tests (`test/scry/test/core/timescaledb_parity_test.exs`, `timescaledb_conn_test.exs`) mirror `postgres_parity_test.exs`/`postgres_conn_test.exs` exactly, `@moduletag :timescaledb`, excluded by default and `async: false` for the same reasons. `config/config.exs` and `mix scry.query`/`mix scry.iex` both gain `--backend timescaledb`.

### Changed

- **`mix scry.query`/`mix scry.iex` moved to `scry_core`** as generic, config-driven tasks any project depending on `scry_core` gets for free -- this package's own copies (`lib/mix/tasks/scry.query.ex`/`scry.iex.ex`) are deleted; a new `config/config.exs` registers this package's own four `Scry.Test.Core.Conn` constructors as named backends (`in_memory` as the default, `ets`, `sqlite`, `postgres`) for `scry_core`'s `Scry.Core.QueryTool`. Non-breaking for this repo's own callers -- same task names, same flags, same output; `test/mix/tasks/scry.query_test.exs`/`scry.iex_test.exs` are unchanged in substance and pass unmodified against the relocated tasks, which doubles as this package's own end-to-end proof that the generic design resolves and runs a real backend set correctly, not just in theory. `mix scry.bench` is unaffected -- it's a benchmark-dataset-generation tool with SQLite-specific baseline-comparison logic, not a thin query-running task, and stays here. See `scry_core`'s own `CHANGELOG.md` for the full motivation (config-driven wiring, not dependency-tree auto-detection, per this project's own already-settled "which kind libraries are loaded is a build-time, not runtime, property" policy).

### Added

- A fourth `Scry.Test.Core.Conn` constructor, `postgres/1` → `scry_engine_postgrex`'s `Scry.Engine.Postgrex`, the same seed data loaded into a real, external Postgres. Genuinely different from the other three in one real way, not just a fourth coat of paint: `in_memory/1`/`ets/1`/`sqlite/1` are all automatically, freshly isolated on every single call (plain in-process data, or a brand-new `:memory:` database); a real Postgres is a persistent, shared, external service instead, so `postgres/1` targets the same fixed `public`-schema tables on every call, idempotently (`DROP TABLE IF EXISTS ... CASCADE` then recreate -- safe to call repeatedly, but genuinely **not** safe to call concurrently with itself). Deliberately not given per-call schema isolation: `Scry.Engine.Postgrex.Schema.column_info/2` hardcodes `WHERE table_schema = 'public'` (that package's own accepted scope decision), so a non-`public` schema would make its own introspection -- and the `NOT NULL` gate every pushed-down query needs -- silently find nothing.
  New `docker-compose.yml` (a disposable `postgres:16` service, `localhost:5433` by default -- a different host port and database name than `scry_engine_postgrex`'s own compose file, so both can run at once with no collision) and a new `mix test.postgres` alias (`test --include postgres`). `postgres/1`'s own tests (`test/scry/test/core/postgres_parity_test.exs`, `postgres_conn_test.exs`) are `@moduletag :postgres`, excluded by default (`test/test_helper.exs`, `ExUnit.start(exclude: [:postgres])`) and `async: false` -- kept in **separate** files from the existing `parity_test.exs`/`conn_test.exs` rather than folding a fourth backend into either one's existing loop, specifically so `mix test`/`mix precommit` stay zero-external-setup for anyone who merely depends on this package for the other three backends. `mix scry.query`/`mix scry.iex` both gain `--backend postgres`.
  Motivated by `scry_engine_postgrex` (built this session, a real, tested Postgres bridging adapter) having explicitly flagged this constructor as its own natural follow-on, and by `impl_spec.md`'s own naming-convention simplification landing in the same window (`scry_engine_relational_postgrex` → `scry_engine_postgrex`; see that package's own `CHANGELOG.md`).

### Changed

- Adapted to `scry_engine_exqlite`'s breaking `execute/3` change: its own direct pushdown path now returns `Scry.Core.Row` values instead of plain maps (that package's own CHANGELOG.md has the full reasoning -- avoids a real, measured per-row map-allocation cost for a caller that doesn't need every field of every row). `Scry.Test.Core.Conn.sqlite/1` itself needed no changes -- it just returns whatever the engine returns -- but every place in this package that assumed a plain-map row directly did: `parity_test.exs`/`conn_test.exs` now normalize via `Scry.Core.Row.to_map/1` before comparing across backends (`in_memory`/`ets` never return `Row`, so this keeps parity assertions meaningful regardless of which backend actually answered), and `mix scry.query`/`mix scry.iex` do the same before printing, so the CLI output stays human-readable (`%{"name" => "Alice"}`, not a raw `%Scry.Core.Row{...}` struct dump) no matter which `--backend` was picked.

  **Re-measured `mix scry.bench --users 1000000` against `scry_engine_exqlite`'s schema-check-caching/`Row`-output/chunk-size fixes** (previous numbers, this same CHANGELOG, same scale: `avg`/`GROUP BY status` ~1.03x, adversarial `GROUP BY user_id` 1.94x): `avg`/`GROUP BY status` stay at genuine parity (~1.0x-1.05x); the adversarial 1,000,000-group `GROUP BY user_id` case drops further, to ~1.53x-1.56x (was 1.94x). A point lookup's own overhead stays high proportionally (~8-10x, though both sides are sub-millisecond in absolute terms) -- now dominated by the fixed cost of the schema-check transaction itself (`BEGIN`/`PRAGMA schema_version`/`COMMIT`), not by anything this round of fixes targeted.

- Validated against `scry_core`'s new single authoritative `Scry.Core.EngineBehaviour.execute/3` callback, replacing `fetch/2,3,4`/`aggregate/5` entirely (see `scry_core`'s own `CHANGELOG.md`). `Scry.Test.Core.Conn.sqlite/1`'s generated schema now declares a real column type (`INTEGER`/`REAL`/`TEXT`, inferred from `Scry.Test.Core.Seed`'s own consistent per-column Elixir value types) and `NOT NULL` on every column, both genuinely true of this fixed dataset and required for `Scry.Engine.Exqlite`'s own `execute/3` to push a `WHERE`/aggregate/ordering comparison down at all -- an untyped, nullable-by-default column would otherwise decline nearly every query in `parity_test.exs`'s own suite. `mix scry.bench`'s own generated `users`/`orders` tables get the identical `NOT NULL` treatment for the same reason (every column there is genuinely always populated by its own row generator). `conn_test.exs`/`native_builder_test.exs`'s "unknown source" tests updated to the new two-constructor error shape (`{:query_error, detail}`, `detail` itself varying by engine rather than a single synthesized `{:no_such_source, source}}` every backend used to produce identically).

  **Re-measured `mix scry.bench --users 1000000` against this pivot, the concrete before/after proof it was worth it** (previous numbers, same scale: `avg(age)` 8.6x-12.9x raw SQL, `GROUP BY user_id` 11.5x-15.3x):

  | query | raw sql | sqlite (via Scry) | overhead |
  |---|---|---|---|
  | point lookup (`WHERE id = <mid> LIMIT 1`) | 29.7 µs | 229.3 µs | 7.73x (fixed per-call cost at microsecond scale, not a scaling problem) |
  | `avg(age)`, no `GROUP BY` | 28.7 ms | 27.75 ms | **1.03x** |
  | `GROUP BY status` (3 groups) + `count`/`avg(age)` | 257.28 ms | 250.69 ms | **1.03x** |
  | `GROUP BY user_id` (~1,000,000 groups, adversarial) | 673.33 ms | 1.306 s | **1.94x** |

  `avg`/`GROUP BY status` now run at native-SQL parity (real `AVG()`/`GROUP BY` pushdown, no Elixir-side re-walk); the adversarial 1,000,000-group case drops from 11.5x-15.3x to 1.94x, the remaining gap now genuinely just row-materialization cost (1,000,000 SQLite rows decoded into 1,000,000 Elixir maps) rather than a full duplicate re-computation.

- `mix scry.bench` now runs every query against a `raw sql` backend too -- the equivalent query issued directly against the open SQLite connection via `Exqlite.Sqlite3`, bypassing Scry entirely -- alongside `sqlite` (Scry query text through `Scry.Core.Executor.run/4`/`Scry.Engine.Exqlite`) and, with `--compare-ets`, `ets`. A new "Scry overhead" comparison table converts the `raw sql` vs. `sqlite` durations into a plain "N.NNx" reading per query, answering "how much does going through Scry actually cost on top of the same database" directly, not just by eyeballing two separate numbers.

- `mix scry.bench` now asks for confirmation before generating anything or running any query -- at the default scale this can take several minutes and uses real CPU/memory/disk, and the task previously gave no indication anything was happening at all until it finished (its own original failure mode, killed mid-run for looking hung). `--yes`/`-y` skips the prompt for scripted/non-interactive use. Database generation now prints its own progress in place (`\r`-updated, rows written so far / total, every 250,000 rows) instead of going silent until done; every benchmarked query prints a line as each of its warmup/timed runs starts and finishes, not just a single aggregate result once all iterations are over. The final summary renders as a box-drawn table (was plain `|`-separated columns); `--compare-ets` runs now also print a second table converting the raw sqlite/ets durations into a plain "N.NNx faster" reading per query.

- `mix scry.bench` now animates a small ASCII spinner (`| / - \`, `\r`-updated in place, same technique `report_progress/2` already uses for generation) for the one class of wait that new-line-per-iteration progress doesn't cover: a *single* call with no count of its own to report while it's running -- a warmup/timed query iteration, measuring memory, building the `orders.user_id` index. `report_progress/2`'s own "rows written so far" is still the right tool wherever there's a real count; the spinner is specifically for "still alive, not hung" on the calls that don't have one. Runs the timed work in a `Task` (`run_with_spinner/2`/`tc_with_spinner/2`) purely so the calling process stays free to keep repainting the line while the work itself blocks -- the work's own result, and any crash, propagate exactly as they would from a direct call.

- **Breaking**: renamed from `scry_test_engine_core` (`ScryTestEngineCore.*`) to `scry_test_core` (`Scry.Test.Core.*`), and restructured around three real, independent engine packages instead of implementing `Scry.Core.EngineBehaviour` itself. `Scry.Test.Core.Conn` no longer exposes `new/1`/`seed/0` against a single built-in engine; it exposes three constructors instead, each returning a ready `{engine_module, conn}` pair, all sharing the exact same `Scry.Test.Core.Seed` dataset:
  - `in_memory/1` → [`scry_engine_inmemory`](https://github.com/joetjen/scry_engine_inmemory)'s `Scry.Engine.InMemory` (no pushdown at all -- the direct successor to this package's own old built-in engine, now its own reusable package).
  - `ets/1` → [`scry_engine_ets`](https://github.com/joetjen/scry_engine_ets)'s `Scry.Engine.ETS` (real O(1) key-lookup pushdown; every seed table gets a declared `id` key via the new `Scry.Test.Core.Seed.keys/0`).
  - `sqlite/1` → [`scry_engine_exqlite`](https://github.com/joetjen/scry_engine_exqlite)'s `Scry.Engine.Exqlite`, loaded into a fresh in-memory (`":memory:"`) SQLite database -- real `WHERE`-clause pushdown, no temp file, nothing to clean up.

  New `test/scry/test/core/parity_test.exs`: the same representative queries (a key-equality filter, a non-key filter, `GROUP BY` + an aggregate, a nested/correlated `SELECT`) run against all three backends and asserted to produce byte-identical rows -- the genuine, automated proof that `Scry.Core.Executor`'s own re-verification is what actually guarantees correctness regardless of engine, not just a documented claim.

  `mix scry.query`/`mix scry.iex` both gain a `--backend in_memory|ets|sqlite` flag (default `in_memory`) picking which constructor serves the query/session -- same seed data either way, only *how* the answer is produced changes.

  `mix scry.bench` now serves its SQLite queries through the real `Scry.Engine.Exqlite` package (connection opened once, reused across every query, real `fetch/3` pushdown) instead of an ad-hoc `Engine` module duplicated inside the task -- the "rows scanned" `:counters` tally that ad-hoc engine used to report is gone with it (`Scry.Engine.Exqlite`/`Scry.Engine.ETS` deliberately don't expose that instrumentation hook; duration and memory already answer "did the pushdown help"). A new `--compare-ets` flag additionally generates a comparably-sized `Scry.Engine.ETS` dataset (same rows, one shared generation pass) and runs every query against it too, side by side with the SQLite numbers -- off by default, since it roughly doubles generation time/memory and the concrete problem this task exists to catch is already fully visible from the SQLite numbers alone. `Scry.Test.Core.Conn.in_memory/1` is deliberately never part of this comparison at benchmark scale (loading millions of rows into a plain Elixir list would just reproduce the original, already-diagnosed problem).

  `lib`/`test` now mirror the new module nesting (`lib/scry_test_engine_core/conn.ex` → `lib/scry/test/core/conn.ex`, etc.), matching every other package in this rename wave. The `mix.exs` app atom also changes, `:scry_test_engine_core` → `:scry_test_core` (unlike `scry_core`/`scry_time_series`, where only the module namespace changed) -- this package was never published, so there's no external app-name compatibility to preserve.

- `ScryTestEngineCore.fetch/2` now returns a genuine `Stream` (`Stream.map(rows, & &1)`) instead of the raw stored list directly, following `scry_core`'s own widened `EngineBehaviour.fetch/2` contract (any `Enumerable.t()`, not just a materialized list -- see `ScryCore.Cursor`'s own moduledoc for the full reasoning). Dogfoods the new contract through a real, separate downstream package, not just `scry_core`'s own test suite.

- `scry_core`'s own `ScryCore.Executor.run/3,4` now returns `{:ok, ScryCore.Cursor.t()}` instead of `{:ok, [row()]}` (bounding `Executor`'s own memory to what a query actually needs, rather than always materializing an entire source). `mix scry.query`/`mix scry.iex` both drain the returned cursor via `ScryCore.Cursor.to_list/1` before printing, folding a lazily-raised `ScryCore.Executor.QueryError` back into the same error-formatting path an eager `{:error, reason}` already used. `README.md`'s own usage examples and `ScryTestEngineCore`'s own moduledoc updated to match. Every existing test asserting on `Executor.run`'s own return value now drains the returned `Cursor` first (a shared per-file `materialize/1` helper) -- confirmed to still pass unmodified otherwise.

### Fixed

- `mix.lock`: `ichor` no longer resolves into this package's own dependency tree at all (regenerated after `scry_core` moved `ichor` back to `only: [:dev, :test], runtime: false` for real -- confirmed via a from-scratch `rm -rf _build deps && mix deps.get`). This package never called anything `ichor`-specific itself; it only ever needed `scry_core`'s own compiled types, which no longer pull `ichor` in as a side effect.

### Added

- `mix scry.bench` -- generates a real SQLite database (via `exqlite`'s own low-level `Exqlite.Sqlite3` NIF API, the same primitive `scry_core`'s own memory-bounding work was measured against) and reports real timing and memory numbers for `ScryCore.Executor.run/4` against a point lookup, a flat aggregate over the whole table, and both a low-cardinality (`GROUP BY status`) and a genuinely high-cardinality (`GROUP BY user_id` on `orders`) grouped aggregate. Moves that measurement out of a throwaway scratch script and into this package as a repeatable benchmark/regression tool -- `exqlite` is a plain, unscoped dependency (`mix.exs`), not `only: [:dev]`-scoped the way `scry_core`'s own `ichor` had to be, since this whole package is test/integration tooling and has no production build of its own to protect. `--users` (default 10,000,000; `orders` is always twice that) controls the generated scale; the database is written to a tmp path (never inside the repo) and deleted again once the run completes, regenerated fresh every time rather than cached, to avoid a stale-data surprise across scale changes.
  Each query runs once, untimed (primes the OS-level file-page cache), then `--iterations` times (default 3), timed via `:timer.tc/1`. Per query: **rows scanned** (a genuine per-row `:counters` tally inside `Engine.fetch/2`, not inferred from the query or the result) vs. **rows returned**; **duration** (avg/min/median/max/stddev across the timed iterations, plus the total); **throughput** (rows scanned per second, and µs per scanned row, both derived from the average duration); and **memory** -- the same *immediate* (right after the call returns) vs. *settled* (after an explicit GC) distinction the memory-only version of this task always reported, now also broken down as settled bytes retained per scanned row. `:erlang.memory(:total)` reports allocator-held memory, not strictly live data, so only the settled number actually answers "did this retain the whole source in memory." A summary table across every query, and the benchmark's own total wall-clock time (database generation included), print at the end.

- Initial project scaffold: `mix.exs` (app `:scry_test_engine_core`, `{:scry_core, path: "../scry_core"}` local path dependency until scry_core is published to Hex), `.credo.exs`/`.formatter.exs`/`.tool-versions`.
- `ScryTestEngineCore.Conn`: the static, in-memory "connection" this engine reads from — a plain `%{source_path => rows}` map, named `Conn` to match the shape a real adapter's own connection/config struct will have (impl_spec.md §2).
- `ScryTestEngineCore`: a full `ScryCore.EngineBehaviour` implementation (`fetch/2`) backed entirely by `Conn`'s static data, returning `{:error, {:no_such_source, source}}` for an unknown source rather than raising.
- `test/scry_test_engine_core_test.exs`: the first real end-to-end integration test of the whole pipeline as a genuinely separate package — query text → `ScryCore.parse/1` → `%ScryCore.Query{}` → `ScryCore.Executor.run/3` → `ScryTestEngineCore` → real static rows. Covers a `where` filter, boolean-logic + multi-field projection, a nested `SELECT` body item, and the unknown-source error path.
- `test/native_builder_test.exs`: the analogous end-to-end proof for `scry_core`'s own Elixir-native front end (impl_spec.md §7 -- `ScryCore.Query`'s Layer 1 functional API and Layer 2's `from/2` macro), from this genuinely separate package rather than `scry_core`'s own test suite. Covers a hand-built Layer 1 query and the equivalent `from/2`-built one executing identically, a `^`-pinned parameter resolved through `run/4`'s own `params` argument, `group_by`/`having`/an aggregate, `from/2` and the equivalent query text producing the exact same rows, and the unknown-source error path via the native builder.
- `ScryTestEngineCore.Seed` + `ScryTestEngineCore.Conn.seed/0`: a reasonably large, realistic, multi-table relational dataset (`users`/`products`/`orders`/`order_items`, with real foreign-key-shaped references between them) available out of the box, alongside (not instead of) `Conn.new/1`'s own existing "supply your own data" path, which is completely unchanged. Motivated by nested `SELECT`/correlation (lang_spec.md §6, and `scry_core`'s own newly-landed nested-`from` support in the native builder) needing something with real relationships to correlate across to be worth exercising at all -- a handful of flat, unrelated rows doesn't exercise that path meaningfully. `test/seed_test.exs` runs a plain filter, `GROUP BY`/an aggregate, and a nested correlation two levels deep (`orders` → their own `order_items`), through both query text and the native builder, confirming both front ends see the same relationships in the same data.
- `mix scry.query` -- runs a query (given as an argument, or via `--file PATH`) against `Conn.seed/0`'s own dataset and prints the resulting rows, for trying the query language out from the command line without writing any Elixir code first. A parse error is formatted via `Ichor.Error.format/1` (the same way `mix ichor.gen`'s own error path does), not a raw struct dump. `test/mix/tasks/scry.query_test.exs` covers both ways of supplying a query, both usage errors (neither given, both given), and the formatted-parse-error case.
- `mix scry.iex` -- an interactive, `iex`-like query prompt against `Conn.seed/0`'s own dataset: a query only runs once it parses, pressing Enter mid-query (a still-incomplete `SELECT ... { ... }`) switches the prompt to `...>` and keeps accumulating lines rather than erroring immediately. `ScryCore`'s own grammar (`Ichor`, a plain backtracking PEG parser) has no incremental/error-recovery parse mode to explain *why* a parse failed, unlike `Code.string_to_quoted/2`'s own dedicated `TokenMissingError` -- confirmed empirically that an incomplete query and a genuinely wrong one return the identical positionless `%Ichor.Error{}`, nothing to tell them apart by. So this never shows a parse error while the buffer might still be added to; a blank line forces the buffer through as it stands and shows whatever comes back (a real result, or the real error), then starts over at `scry>`. Ctrl+D (EOF) exits. `test/mix/tasks/scry.iex_test.exs` covers a single-line query executing immediately, a multi-line one only executing once complete, a leading blank line being a no-op, and a never-going-to-parse query sitting until a blank line forces it through and resets the prompt.
- `mix scry.iex` also gets real Up/Down arrow-key history, when run as `iex -S mix scry.iex` instead of plain `mix scry.iex` -- verified against a real pty (`python3`'s own `pty` module, not just asserted): plain `mix scry.iex` boots the VM with `-noshell`, so an arrow key lands as a literal `^[[A` escape byte sequence with no editing at all, while `iex -S mix scry.iex` boots a real interactive `iex` session first and runs this task's loop *inside* it, where an ordinary `IO.gets/1` read gets the exact same OTP group-leader line editing/history `iex`'s own prompt runs on -- zero code of this task's own involved, this isn't something implemented here, just discovered and documented. Plain `mix scry.iex` now prints a one-line startup note pointing at the `iex -S` invocation, gated on `IEx.started?/0` being `false` so it disappears once actually run that way (`:init.get_argument(:noshell)` was tried first and rejected -- it reports `-noshell` under `iex -S mix` too, `IEx.started?/0` is the signal that actually tracks reality).

### Fixed

- `scry_core`'s own `ichor` dependency had to be un-scoped from `only: [:dev, :test]` to compile at all as a dependency of this package — see `scry_core`'s own changelog and impl_spec.md's Open Implementation Risks for the finding; this package's `mix.exs` needed no changes of its own once that was fixed.
